# `index.html` 프리렌더 마크업 경량화 기록 (1단계 실행 완료)

> 작성: 2026-09-18 · 상태: **1·2단계 실행 완료(빈도순 어휘 · 혼동 어휘) · 나머지 블록은 실측 후 보류 판단**
> 관련 기록: `docs/app-split-plan.md`(스타일·스크립트·데이터 분리) · `docs/ux-review.md` §20

## 0. 왜 이 문서가 필요한가

스타일(`assets/app.css`)·스크립트(`assets/app.js`)·데이터(`data/app-data.js`)를 모두 파일로 뺀 뒤에도
`index.html` 에 남은 큰 덩어리는 **프리렌더 마크업**입니다. "그럼 이것도 파일로 빼면 되지 않나?" 가
자연스러운 다음 질문인데, **그 답은 "아니오"에 가깝습니다** — 그 이유와 대안, 실제로 한 일을 정리합니다.

## 1. 1단계 — 빈도순 기출 어휘를 별도 페이지로 분리 ✅ (2026-09-18)

`freqGrid`(빈도순 기출 어휘 200개)는 프리렌더 블록 가운데 가장 컸고(48.6KB), 성격도 홈의 도구 섹션들과
달리 **"검색 없이 끝까지 읽는 참고 목록"** 이었습니다. 그래서 이 한 덩어리만 별도 정적 페이지로 옮겼습니다.

| | 1단계 전 | 1단계 후 |
| --- | --- | --- |
| `index.html` (문자 수 · 프리렌더 로그와 같은 기준) | 239.2KB | **196.1KB** (−43.1KB) |
| `index.html` (디스크 바이트) | 288.6KB | **235.6KB** |
| 프리렌더 블록 합계 | 약 165KB | **121.7KB (전체의 62.1%)** |
| `freqGrid` 프리렌더 | 48.6KB · 단어 200개 | **4.9KB · 단어 20개 + 전체 목록 링크** |
| 색인 페이지 / 사이트맵 URL | 124개 | **125개** |

- 새 페이지: `units/frequency.html` (93.6KB · 단어 200개 + 구간 이동 + 학습 순서 + FAQ + 내부 링크).
  생성기 `build-pages.mjs` 의 `buildFrequencyPage()` 가 만들고, 데이터는 `data/extra.js` 의 `frequency`(앱이 쓰는 값) 그대로입니다.
- 홈 동작은 그대로입니다 — 앱(`renderFrequency`)이 로드될 때 인자 없이 다시 그려서 사용자는 200개를 모두 봅니다.
  프리렌더(`prerender-home.mjs` 의 `args: '"", 20'`)만 20개를 심습니다.
- 앱 쪽 변경은 함수 하나입니다: `renderFrequency(filter, limit)` — `limit` 은 "미리 심을 때만" 쓰는 인자입니다.
- 내부 링크: 홈 섹션의 「전체 목록 보기」 · 단어장 허브(`units/index.html`)의 「함께 보면 좋은 자료」 ·
  `<noscript>` 목차(정적 링크 6 → 7개) · 새 페이지에서 홈·단어장·숙어·가이드·문법 요약으로 나가는 링크.
- 검증: `npm run build` · `npm run audit`(색인 페이지·사이트맵·문서 수치) · `npm test` · `npm run check:browser` ·
  `npm run check:staged` · `npm run perf:compare` 모두 통과.

## 1-b. 2단계 — 혼동 어휘 카드도 별도 페이지로 ✅ (2026-09-18)

`confuseGrid`(혼동 어휘 20쌍·17.2KB)를 `units/confusion.html` 로 옮겼습니다. §4 의 보류 기준(홈 240KB 미만·
블록 25KB 미만)에는 아직 못 미치지만, 아래 두 가지를 확인하고 실행했습니다.

1. **학습 흐름이 깨지지 않습니다** — 홈의 카드는 앱이 로드되면 어차피 20쌍을 다시 그립니다. 프리렌더에서 줄이는
   것은 “미리 심어 두는 양”뿐이고, 화면에서 보이는 카드 수는 그대로입니다(빈도순 어휘와 같은 방식).
2. **검색으로 들어올 주제입니다** — “affect effect 차이”처럼 짝을 검색해 바로 오는 유입이 있어,
   카드에 예문·구분 팁·예문 발음을 모두 담은 페이지가 홈 섹션보다 유리합니다.

| | 2단계 전 | 2단계 후 |
| --- | --- | --- |
| `index.html` (문자 기준) | 196.5KB | **184.4KB** (−12.1KB) |
| `confuseGrid` 프리렌더 | 17.2KB · 20쌍 | **5.1KB · 6쌍 + 전체 목록 링크** |
| 색인 페이지 / 사이트맵 URL | 125 / 125 | **126 / 126** |

- 새 페이지: `units/confusion.html` (45.8KB · 20쌍 전체 + 학습 순서 + FAQ 4문항 + 내부 링크 · 예문 발음 버튼 40개).
- 데이터는 홈 앱과 **같은 값**(`data/app-data.js` 의 `CONFUSABLES`)을 써서, 두 곳의 내용이 어긋날 일이 없습니다.

## 2. 실측 — 남은 프리렌더 블록 (2026-09-18)

`index.html` 196.1KB 가운데 프리렌더 블록은 121.7KB(62.1%)입니다. 큰 것부터:

| 블록 | 크기 | 내용 | 판단 |
| --- | --- | --- | --- |
| `mnemonicGrid` | 11.2KB | 어원 암기 팁 20개 | ⏸ 보류 |
| `wordpartGrid` | 11.0KB | 어근·접두사 24개 | ⏸ 보류 |
| `templateGrid` | 10.5KB | 이메일·회의 템플릿 11개 | ⏸ 보류 |
| `readingGrid` | 9.2KB | 리딩 미니 지문 10개 | ⏸ 보류 |
| `sprintBox` | 7.9KB | 30일 스프린트 30개 | ⏸ 보류 (진행률을 앱이 다시 그림) |
| `wordfamilyGrid`·`idiomGrid`·`noscript` | 각 5~6KB | — | 그대로 |
| 나머지 8개 블록 | 각 1.7~4.9KB | — | 그대로 |
| 합계 | 121.7KB | 18개 블록 | — |

> 참고: 실제 **전송량**은 문제가 아닙니다. 배포본 홈 문서는 gzip 약 48KB 로, 첫 방문 총량도
> `npm run perf:compare` 로 계속 확인하고 있습니다. 남는 비용은 ①저장소 원본의 편집·리뷰 크기,
> ②CI 가 매번 훑는 파일 크기, ③첫 로드의 DOM 노드 수입니다.

## 3. "파일로 빼면 안 되는" 이유 (핵심)

프리렌더의 **목적 자체가 그 내용을 `index.html` 안에 두는 것**입니다(`tools/prerender-home.mjs` 도입 이유):

- 자바스크립트를 실행하지 않는 크롤러(네이버 Yeti 등)가 읽어야 합니다.
- 자바스크립트를 끈 사용자도 내용을 읽을 수 있어야 합니다.

그래서 프리렌더 내용을 `data/*.js` 처럼 **외부 파일로 옮기면 목적이 사라집니다**. 선택지는 "옮기기"가 아니라
**"줄이기" 또는 "별도 정적 페이지로 나누기"** 뿐입니다.

## 4. 2단계 판단 — 나머지 블록은 지금 옮기지 않습니다

| | 방안 | 효과 | 비용·위험 | 판단 |
| --- | --- | --- | --- | --- |
| A | 그대로 둔다 | 0 | 없음 | ✅ 기준선 |
| B | 참고 목록 블록을 별도 페이지로 | **−43KB**(빈도순 어휘) · **−12KB**(혼동 어휘) | 새 페이지·링크·수치 갱신 | ✅ **1·2단계로 실행 완료** |
| C | 남은 학습 카드 블록까지 쪼개기 | 블록당 4~11KB | 블록마다 새 페이지·링크·감사 수치 갱신, 학습 흐름 이원화 | ⏸ **보류** |
| D | 홈을 2~3개 정적 페이지로 분할(어휘/훈련/시험) | 가장 큰 감소 | 앱 상태·딥링크·`check-browser` 100여 항목이 모두 홈 전제라 위험 큼 | ⏸ 보류 |
| E | 프리렌더를 JS 로 주입 | — | §3 의 목적이 깨짐 | ❌ 안 함 |
| F | 프리렌더 분량 자체를 줄임(항목 수 축소) | 큼 | 검색·학습 내용이 줄어듦(콘텐츠 손실) | ❌ 안 함 |

**C 를 보류한 근거(실측)**

1. 남은 블록은 최대 11.2KB 입니다. 1단계(−43KB)·2단계(−12KB)에 비해 이득이 1/4 이하로 떨어집니다.
2. `mnemonicGrid`·`wordpartGrid`·`templateGrid`·`readingGrid` 는 **앱의 도구 화면과 얼굴을 맞대고 쓰는 카드**라
   목록만 때어 별도 페이지로 만들면 “읽으면서 바로 외우던” 흐름이 두 갈래로 찢어집니다.
3. 블록마다 새 정적 페이지 + 내부 링크 + `audit-site` 수치(`pages`·`sitemap_urls`) + 문서 갱신이 따라붙어,
   페이지 수가 늘어날수록 "고아 페이지"·중복 콘텐츠 위험이 함께 커집니다(지금은 0건).
4. `sprintBox` 는 앱이 진행률을 다시 계산해 그리는 값이라, 프리렌더는 어차피 "0% 기준" 안내입니다.

**다시 판단할 조건**: ①`index.html` 이 다시 240KB 를 넘어설 때, ②블록 하나가 25KB 를 넘길 때,
③검색 유입이 특정 주제(예: 리딩 지문)에 몰려 그 주제만 따로 랭크시킬 필요가 생길 때.

## 5. 검증 방법

```bash
npm run build          # 생성기 + 프리렌더 (결과물 커밋 대상)
npm run verify         # 생성물이 HEAD 와 어긋나지 않는지 (프리렌더 --check 포함)
npm run audit          # 링크·자산·사이트맵·문서 수치 (색인 페이지 수 변화 반영)
npm run check:browser  # 홈 섹션·이동·딥링크가 그대로인지 (100여 항목)
npm run check:staged   # 배포본에서도 같은지
npm run perf:compare   # 첫 방문 총량이 늘지 않았는지
npm run audit:external # 배포 후 색인·링크 상태
```

색인 관점 확인: 새 페이지가 `sitemap.xml` 에 있고, 홈·허브에서 내부 링크로 닿는지(`audit-site` 3-1).

## 6. 하지 않을 것

- 프리렌더 내용을 JS 로 채우기(§3).
- 홈의 앱 구조·딥링크·화면 전환을 건드리기(1단계는 생성물 추가 + 프리렌더 분량 축소뿐).
- 콘텐츠 항목 수 줄이기(검색·학습 가치 손실).
